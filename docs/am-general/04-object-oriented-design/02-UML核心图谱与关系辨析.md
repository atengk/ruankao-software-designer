## 一、 核心考纲与概念辨析

### 1. UML 图谱全景分类矩阵（静态结构图 vs 动态行为图）

统一建模语言 (UML 2.x) 共有 14 种图，软考重点考查以下常用图：

| 大类 | UML 图名称 | 核心用途与图元要素 | 上/下午考查特点 |
| :--- | :--- | :--- | :--- |
| **结构图 (静态图)** | **类图 (Class Diagram)** | 描述系统中的类及其接口、属性、方法以及类之间的静态关系 | **必考**，贯通下午题 3 与设计模式 |
| | **对象图 (Object Diagram)** | 描述某一特定时间点上类的具体实例（对象）及其属性值和链 | 类图在某瞬间的“快照” |
| | **构件图/组件图 (Component Diagram)** | 描述软件代码构件、模块、库及接口之间的物理组织 | 系统物理架构划分 |
| | **部署图 (Deployment Diagram)** | 描述软件运行时的硬件节点、物理拓扑及软件构件在节点的部署配置 | 硬件/环境部署 |
| **行为图 (动态图)** | **用例图 (Use Case Diagram)** | 描述参与者（Actor）与用例之间的业务功能关系，刻画系统外部需求 | **必考**，下午题 3 需求分析高频考点 |
| | **顺序图/时序图 (Sequence Diagram)** | 按**时间顺序**展示对象之间交互消息传递的动态协作 | **必考**，重点在时间顺序、生命线、激活期 |
| | **通信图/协作图 (Communication Diagram)** | 强调收发消息的对象的**组织结构**，用序列号标明消息执行次序 | 与时序图语义等价，可无损互转 |
| | **状态机图/状态图 (State Machine Diagram)** | 描述对象在其生命周期内经历的各种**状态、事件触发及状态转移** | 适合具有复杂状态流转的对象（如订单流转） |
| | **活动图 (Activity Diagram)** | 描述业务流程或计算逻辑中的工作流控制流与并行分支（分岔与汇合） | 类似于流程图，但支持并发泳道 |

### 2. 类图 6 大关系权威辨析（强弱顺序排列）

类间关系由弱到强的顺序为：
$$\text{依赖 (Dependency)} < \text{关联 (Association)} < \text{聚合 (Aggregation)} < \text{组合 (Composition)} < \text{泛化 (Generalization)} \approx \text{实现 (Realization)}$$

```
【依赖】 - - - - >    带箭头的虚线
【关联】 ───────>     带箭头的实线（或无箭头的双向实线）
【聚合】 ◇───────>     空心菱形 + 实线箭头（菱形在整体端）
【组合】 ◆───────>     实心菱形 + 实线箭头（菱形在整体端）
【泛化】 ───────▷     空心三角箭头 + 实线（箭头指向父类）
【实现】 - - - - ▷    空心三角箭头 + 虚线（箭头指向接口）
```

| 关系名称 | 语义本质 | 典型代码表现 / 现实映射 | 图形符号表示 |
| :--- | :--- | :--- | :--- |
| **依赖 (Dependency)** | `uses-a`（使用关系）：某类在其方法参数、局部变量或静态调用中使用了另一类的对象 | `void drive(Car car)` 中的参数 | **带箭头的虚线**（指向被使用者） |
| **关联 (Association)** | `has-a`（持有关系）：类之间的长期结构化引用，彼此平级 | 作为类的成员变量：`private Person customer;` | **带箭头的实线**（或无箭头双向实线） |
| **聚合 (Aggregation)** | `has-a`（部分与整体）：部分可以脱离整体而独立存在，“同生不同死” | 汽车与轮胎；班级与学生 | **空心菱形 + 实线箭头**（菱形位于整体端） |
| **组合 (Composition)** | `contains-a`（部分与整体）：部分不可脱离整体独立存在，“同生共死” | 人与大脑；公司与部门 | **实心菱形 + 实线箭头**（菱形位于整体端） |
| **泛化 (Generalization)**| `is-a`（继承关系）：子类继承父类的属性和方法 | Java 中的 `extends` 继承基类 | **空心三角箭头 + 实线**（指向父类） |
| **实现 (Realization)** | 类实现接口所定义的契约规范 | Java 中的 `implements` 实现接口 | **空心三角箭头 + 虚线**（指向接口） |

### 3. 用例图三核心关系混淆辨析（高频扣分点）

- **包含关系 (`<<include>>`)**：
  - **核心特征**：基础用例执行时**必须无条件执行**被包含用例。抽取出多个用例公共的子功能，避免冗余。
  - **箭头方向**：**从基础用例指向被包含用例**（虚线箭头，标注 `<<include>>`）。
  - **口诀**：买手机必须包含“支付”。

- **扩展关系 (`<<extend>>`)**：
  - **核心特征**：在特定扩展点和满足特定条件时，被扩展用例才可能被执行。基础用例自身功能是完整的，被扩展用例提供的是**附加或可选行为**。
  - **箭头方向**：**从扩展用例指向基础用例**（虚线箭头，标注 `<<extend>>`）。
  - **口诀**：买手机可选“加购碎屏保”（碎屏保指向买手机）。

- **泛化关系 (Generalization)**：
  - **核心特征**：通用用例与具体特化用例之间的父子继承关系。
  - **箭头方向**：**从子用例指向父用例**（实线空心三角箭头）。
  - **例子**：微信支付、支付宝支付指向“在线支付”。

## 二、 命题题眼与陷阱防御

> [!CAUTION]
> ### 🚨 常见命题陷阱盘点
> 1. **聚合与组合的菱形混淆**：
>    - 空心菱形 = **聚**合（松散，能分开）；
>    - 实心菱形 = **组**合（紧密，不能分开，同生共死）。**菱形永远画在“整体（Whole）”这一侧**，绝不能画在“部分（Part）”一侧！
> 2. **包含与扩展的箭头方向极易颠倒**：
>    - 包含 `<<include>>`：**主用例 $\rightarrow$ 被包含用例**（我要做 A，必须顺带做 B，故 A 指向 B）；
>    - 扩展 `<<extend>>`：**扩展用例 $\rightarrow$ 主用例**（B 是对 A 的补充，故 B 指向 A！）。出题人 80% 的选项都会把扩展关系的箭头方向倒置！
> 3. **时序图与协作图的互转等价性**：时序图强调时间序列，协作图强调空间拓扑。二者在表达动态协作上完全等价，可无损相互转换。
> 4. **活动图的分岔 (Fork) 与汇合 (Join)**：分岔表示一条控制流分支为多条**并发**控制流；汇合表示多个并发流必须全部到达后才能继续向下执行，使用粗水平黑横条表示。

## 三、 典型真题溯源与验证

### 【真题精选 1】（考查用例图关系判断）
**题干**：在 UML 用例图中，（ ）关系用于说明一个用例在特定条件下会向另一个基础用例追加行为，此时虚线箭头的方向是由（ ）指向（ ）。
A. 包含；基础用例；被包含用例  
B. 扩展；基础用例；扩展用例  
C. 扩展；扩展用例；基础用例  
D. 泛化；子用例；父用例  

**【答案】**：**C**  
**【解析】**：
扩展关系（`<<extend>>`）用于在满足扩展点条件时为基础用例增加可选行为。扩展关系的虚线箭头方向规定为**由扩展用例指向基础用例**。A 选项虽然描述了包含，但题干强调“特定条件下追加行为”，属于扩展关系的特征；B 选项箭头方向错误。

---

### 【真题精选 2】（考查类图关系强弱与同生共死特征）
**题干**：某在线销售系统中，订单（Order）由多个订单项（OrderItem）组成，当一个订单被删除时，属于该订单的所有订单项也必须随之被删除，不能独立存在。在 UML 类图中，Order 和 OrderItem 之间最恰当的关系是（ ）。
A. 依赖关系  
B. 关联关系  
C. 聚合关系  
D. 组合关系  

**【答案】**：**D**  
**【解析】**：
订单（整体）与订单项（部分）之间具有强烈的生命周期依赖，“同生共死”，部分不能脱离整体独立存在，因此属于**组合关系（Composition）**，在类图中以实心菱形实线箭头表示，实心菱形位于 Order 端。如果是部门与员工、学校与教师，教师离职后仍独立存在，则属于聚合关系（空心菱形）。
